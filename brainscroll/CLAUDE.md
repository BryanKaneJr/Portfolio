# BrainScroll: notes for AI coding agents

Read `docs/product-rules.md` before changing anything that touches progression, XP, Brainpower, IDs or content. Those rules are contracts. The full product specs live in `docs/specs/*.md` (Markdown is the working source; `docs/source/*.docx` are snapshots). When a product rule changes, update the spec, the digest in `docs/` and the code together.

## Commands (run from `brainscroll/`)

- `npm run check`: typecheck all workspaces, lint the app (hook-order bugs are errors), lint copy for em dashes, run core, scripts and admin unit tests, and validate `content/`. Run it before every commit.
- `npm run content:build`: after editing anything in `content/`, recompile `app/src/content/built/` (a small index loaded at launch, plus one lessons file per skill loaded on first use). `check` fails if it's stale.
- `npm run art:sync`: after adding level art to `app/assets/images/art/` (named by image ID), regenerate `app/src/content/art.ts`. `check` fails if it's stale. Each level's `art` field names its image (`docs/image-manifest.md`).
- `npm run test:db`: apply `backend/supabase/migrations` to a temp Postgres, then run each `backend/tests/*.test.sql` in a fresh copy of the database. `content-import.test.sql` uses the real `content/`.
- `npm run content:import`: validate and publish `content/` through the `import_content` RPC. Use `--sql <file>` to write SQL instead.
- `npm run e2e` / `npm run e2e:remote`: build the web app and drive it with Playwright. Remote mode runs it against real migrations and content through `backend/tests/fake-supabase.mjs`. Run both after changing screens or progress code.
- `npm run screens`: the same web build walked through every screen a learner sees, saved as phone-size PNGs in `./screens` (`SHOT_OUT`, `SHOT_W`, `SHOT_H` set the folder and viewport, e.g. 430×932 for App Store images). Use it to look at UI changes.
- `npm run supabase:check`: validate the app's Supabase URL/key (never a secret key) and, with network, probe the project read-only. See `docs/supabase-setup.md`.
- `npm run insights:pull`: pull aggregate learner insights and open content reports from Supabase (service key) into `admin/.data/` for the admin. See `docs/analytics.md`.
- `npm run app:preview`: the web app in local mode for Cloudflare Pages (`app/dist-preview`), the preview on every branch. See `docs/app-preview.md`.
- `npm run site:build`: build the invite site (`site/src` → `site/dist`) with the Universal Link / App Link files, from public IDs in the environment. See `docs/invite-links.md`.
- `npm run admin`: the local Content Admin (http://127.0.0.1:4321). It browses, edits, validates and previews levels in `content/` and controls draft/published (see `admin/README.md`).
- `npm run app`: Expo dev server. In `app/`, use `npx expo install <pkg>` to add dependencies (it picks SDK-compatible versions). See `app/AGENTS.md`.

## Invariants

- **No em dashes (U+2014) in anything BrainScroll-authored**: curriculum, UI copy, docs, errors, comments, generated content. Rewrite the sentence (comma, colon, semicolon, parentheses, period or conjunction); never substitute mechanically. Only verbatim source quotes (`supportingQuote`) and source title/publisher/URL are exempt. `validate:content` and `lint:copy` (both in `check`) enforce it; see `docs/content-guide.md` "Editorial rules".

- **Never send the owner's personal details anywhere.** Scripts, fact-checkers and agents that make web requests must not put an email address, name or username in a User-Agent, query string, header or payload. Use `User-Agent: BrainScroll content review` (no contact address). This applies to briefs you write for subagents too: tell them.

- The server owns completion, XP, Brainpower and entitlements. The client animates results returned by `complete_level`; it never computes awards itself.
- XP is an immutable ledger (`xp_events`) with a unique `(user_id, idempotency_key)`. Never add a mutable XP counter as the source of truth.
- Visible skill level = highest canonical level cleared. It is never derived from XP.
- BrainScroll is a learning app, not a quiz app. Regular levels are hook → 2–5 focused learning cards (~150–320 words that make one concept memorable; learn > interesting > fun, no tangents) → **3 questions** (recall, understanding, connection). Only checkpoints (5), the Level 50 milestone (7) and the Level 100 Mastery Challenge (10) test more. These canonical counts live in `LEARNING_STRUCTURE[type].questions.standard` (also exported as `STANDARD_QUESTIONS`); never hard-code them, and never describe them as ranges.
- Weekly Knowledge Quests (post-MVP) count only new levels, and their progress is **derived from `LEVEL_COMPLETE` rows in `xp_events`** (plus, for a skill with no new levels left for the learner, `CHAPTER_REVIEW` rows with reason `no_new_levels`, one per chapter). Never add a separate quest counter, a second XP total, or anything that stores levels or trophies twice. Quests are free-completable, move to the Archive after their week, and must not block the MVP. The trophy (and the title and emblem it unlocks) is only for a live-week clear; the Archive still pays the XP bonus (owner, 2026-09-29). Nothing dwarfs a level: keep every award in proportion to a regular level's 100 XP.
- Level completion is **first attempt → reinforcement → resolution → progression**. Every attempt goes through `answer_question` (first attempt recorded once, immutable); `complete_level` requires every question resolved and awards XP from first attempts only, from each level type's own pool (`LEARNING_STRUCTURE[type].firstAttemptXp` / `level_xp_curve`; never hard-code XP in the UI). Corrections never add XP. A perfect level straight after other perfect levels pays the perfect streak's extra in the same event (`perfectStreakBefore` / SQL `perfect_streak_before`, +10% per level in a row up to `XP.PERFECT_STREAK_MAX_PERCENT`); only level first clears build or break it, never reviews. Level 100·k earns the ★ by being resolved, with no minimum score and no separate bonus. Review works the same way: `submit_review` records the first attempt per scheduled occurrence (+10 if right, except the re-check after a missed review and a question whose answer was checked outside review since it came due), a miss must be corrected with its source cards, and the answer is never revealed. **First attempts set reward and memory strength; resolution sets completion and progression.** Chapter reviews (`start_chapter_review` / `answer_chapter_review` / `complete_chapter_review`, core `chapterReview.ts`) are graded the same way but pay at most `XP.CHAPTER_REVIEW_MAX` (30) per review, may be repeated, and never move concept strength, the review schedule, Brainpower spending or the streak (a chapter's first completed review earns +1 Brainpower); each answer is noted as a check, and a first try whose question was checked outside the review since it started (a replay) doesn't count as right. Never grade from bundle `correct` flags in remote mode: learners get stripped bundles (`learner_bundle`).
- **An account comes first; there is no guest mode.** Learners sign in (Apple or Google at launch; the phone and email code flows exist but are off, see `EXPO_PUBLIC_SIGN_IN_METHODS`) before any progress exists. Never call `signInAnonymously`, keep device-only or guest progress, or add guest migration, merge or cleanup. The database refuses anonymous users (`handle_new_user`). Device-side state (sessions, onboarding, active skill) is keyed per account. See `docs/accounts.md`.
- **Account deletion must stay complete.** `delete_my_account()` deletes the auth user, and everything cascades through `profiles`. Any new table holding a learner's data must reference `profiles (id) on delete cascade`, and `account-deletion.test.sql` must list it.
- Every question has `sourceCardIds`. A wrong answer shows those canonical cards; never generate recovery text at runtime.
- Stable IDs only (`level.science.astronomy.001`). Never key anything by display name.
- Published `level_revisions` are immutable. To correct content, publish a new revision.
- The app talks to progress only through `ProgressBackend` (`app/src/progress/backend.ts`). `remoteBackend.ts` calls Supabase RPCs, and `localBackend.ts` is the development harness (shared rules on-device, simulated accounts, used only without Supabase config). Keep both implementations in step.
- Local play (`app/src/progress/localBackend.ts`) runs `completeLevel` from `packages/core/src/completion.ts`, which mirrors the SQL `complete_level`. The same goes for `buildReviewQueue`/`submitReview` and `get_review_queue`/`submit_review`, and for `chapterReview.ts` and the chapter review RPCs (`chapterReview.test.ts` / `chapter-reviews.test.sql`). If you change one, change the other, and keep `completion.test.ts`/`review.test.ts` in step with `core-loop.test.sql`/`review.test.sql`.
- **Every UPDATE or DELETE in a SQL function needs a top-level WHERE.** Hosted Supabase runs API calls with pg-safeupdate, which rejects them otherwise; local Postgres doesn't, so `scripts/test/sql-safe-update.test.ts` (in `check`) guards it.
- Constants live in `packages/core/src/constants.ts` **and** `app_settings` / SQL helpers in the migration. Change both together.
- Analytics measure learning and product health, never time spent: no durations, session lengths or engagement minutes. Client events must be in `ANALYTICS_EVENTS` (core) **and** `analytics_event_names` (SQL); props are flat and PII-free. See `docs/analytics.md`.
- The learning streak is derived (SQL `learning_streak`, core `learningStreak`) from learning days: each first clear or scheduled review answer notes its day in `user_learning_days` (core `learningDays`) as it happens, in the time zone the learner is in then, and days are never re-dated, so a later time zone change or content correction can't merge or remove one. It is never used for guilt or fear: no on-screen warnings, countdowns or freezes. Reminders may push it, and the app should notify people (owner, 2026-10-01: "we want people to use the app"), but never as a jerk: no guilt, threats or fake deadlines (core `reminders.ts` and its copy test). Its rewards are the permanent streak trophies (7, 30, 100, 365, 500, 1,000 days; `STREAK_TROPHY_TIERS`), earned by the longest run ever and never taken away, and +1 Brainpower the first time each day it's extended (day 2 on); nothing else (XP, cosmetics) is tied to it.
- **Brainpower** (owner, 2026-10-02) paces free learners: refill to 5 each local day (more is kept), at most 10 (anything earned at 10 is lost), and 1 is spent when a new level is first cleared; nothing else costs it, and wrong answers never do. +1 for extending the streak (once a day), every trophy, a chapter's first completed chapter review, a 10% truly random drop on a perfect first clear (no pity), and each Weekly Quest goal met and each quest completed (owner, 2026-10-03; SQL `brainpower_sync_quests`, core `questBrainpower`), and +2 from a map chest, rolled only when both fit. Unlimited is ∞. The server is authoritative (`user_brainpower`, `brainpower_awards`, triggers in migration 20261031000000, `daily_status_for`); core `brainpower.ts` mirrors it for local play (`brainpower.test.ts` / `brainpower.test.sql`). Each award is recorded once by key, so nothing pays twice.
- **Map chests** (owner, 2026-10-05; `docs/specs/REWARDS.md`, core `rewards.ts`, SQL `open_chest` / `start_boost` / `set_look`): one per chapter after its 5th level, opened once, rolled on the server from `app_settings.chest_loot` (core `CHEST_LOOT` mirrors the defaults). A roll that can't pay out (Brainpower without room for both points, Unlimited, a cosmetic tier above the learner's Knowledge Level or fully owned) becomes the 15-minute boost, so a chest never pays a duplicate. XP boosts (15, 30, 60 minutes) wait on Profile until started, run one at a time and make a level's first clear pay 2.0x, the perfect streak included, never more; one `LEVEL_COMPLETE` event, so they count toward the league. Cosmetics (glows behind the avatar, ids `ring.*`; name styles; titles) are drawn in code; keep core `COSMETICS` and the `cosmetic_items` seed identical (`rewards-sync.test.ts`). A skill's first Mastery star earns its "<Skill> Master" title. One title shows at a time (a look title or a quest title). Chests are never sold, and Unlimited changes nothing in them but the Brainpower roll.
- Don't add ads, other currencies, lives (the feed's like heart is not a life), streak punishment, or paywalled subjects. Unlimited's only progression effect is ∞ Brainpower; it may carry cosmetic/personalization perks, but never XP, knowledge, trophies or accomplishment cosmetics (those stay earned). Social ships before launch (owner, 2026-10-01): friends (invite link or exact username), weekly leagues of up to 20 matched by brain level with 1,000 / 500 / 250 XP prizes (`LEAGUE_FINISH`), and a feed derived from existing records with hearts as the only reaction (owner, 2026-10-03). No comments, messages or public posts; block and report on every profile; social tables are RPC-only. Usernames pass one filter, server and app alike: keep `usernameFilter.ts` (core) and the `username_terms` seed identical (`username-terms.test.ts`); reports are worked in the admin's Learner reports queue (`docs/moderation.md`). Invite links are `https://<EXPO_PUBLIC_INVITE_DOMAIN>/invite/CODE` served by `site/` (`docs/invite-links.md`). Social push notifications are queued by database triggers into `notification_outbox` and sent by the `send-push` function under `claim_social_pushes`' rules (opt-out switch, 9 am to 9 pm local, at most 4 a day); their copy lives in `functions/_shared/push.ts` with its own no-jerk copy test (`docs/notifications.md`). Keep `social.ts` (core), `social.test.sql` and `localSocial.ts` in step with the migration. Challenges stay post-MVP and never time/speed-based. See CURRENT_PRODUCT_DECISIONS §22 and "Never build" in the product rules.

## UI

- Build screens from `app/src/components/ui` primitives and `theme/tokens.ts`; don't restyle raw views. **Learning mode is quiet and progression mode is loud:** no glow, gold, XP or stats on lesson screens, and gold only for mastery (exceptions: Unlimited's permanent gold brain with ∞, owner 2026-10-02; the Gold ring and name style won from chests, owner 2026-10-05). Reward rarities have one material each (`components/rewardsUi.tsx`: Common silver, Rare sapphire, Epic amethyst, Legendary sunset orange; Mastery titles gold, Quest titles violet); use them, don't restyle. See `docs/design-system.md`.
- **Dr. Scroll** (the mascot) appears only through spots: `DrScroll` / `DrScrollSays` with a `spot` from `MASCOT_SPOTS` (core), never a raw image. Artwork is wired in `app/src/components/ui/mascotArt.ts` only. His colour is `plum` (speech bubbles, tips, "Did you know"); never use it for actions or progress. See `docs/mascot.md`.
- Questions are select → CHECK. Only a checked answer is an attempt, and the first checked answer is the first attempt. Three kinds (owner, 2026-10-03): multiple choice, **match** (pair each left item with its partner) and **order** (put items in order; drag with tap-to-swap as backup). Match and order are graded by label, so identical labels are interchangeable; an answer travels as one string (an option id, or a JSON array of labels: core `answers.ts`, SQL `grade_answer`); a miss marks the wrong positions, never what belongs there; phones never receive the answer (`learner_question`). A multiple-choice prompt with one gap (`_____`) is a **fill in the blank** (core `blank.ts`, app `FillBlank.tsx`): same grading, the pick drops into the sentence. Keep e2e helpers (`e2e/helpers.mjs`) in step with the interaction.

## Layout

`app/` (Expo Router, routes in `app/src/app/`), `packages/core/` (shared rules + zod schema), `backend/` (Supabase), `content/` (curriculum JSON), `scripts/` (validator), `admin/` (local content admin), `docs/`.
